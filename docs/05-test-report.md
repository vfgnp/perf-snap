## 3. 保存の時間とサイズ

| 条件 | 保存にかかった時間 | ファイルサイズ |
|---|---|---|
| 1 回目（オプションなし） | 34〜49 秒 | 190〜1,072 MB |
| `-skipPdbGen`（2 回目の既定） | 34.8 秒 | 420 MB |
| `-skipPdbGen -compress` | 42.6 秒 | **146 MB（約 1/3）** |

- `-skipPdbGen` を付けても時間はほぼ変わらなかった。時間の大半は、メモリ上のデータをファイルへ書き出す処理と考えられる。
- `-compress` を付けると時間は約 8 秒延びるが、サイズが約 1/3 になる。容量の上限が 10 GB なので、**圧縮を既定にすると残せる回数が約 3 倍になる**。→ §6 で提案。

## 4. 未解決の問題：フライトレコーダーのメモリ使用量

- 組み込みプロファイルのメモリーモードは、**PC の搭載メモリに応じて大きなバッファを確保する**。この PC（7.7 GB）では約 1.3 GB だった。
- このメモリはカーネルの非ページ プール（ディスクに逃がせないメモリ）なので、**監視そのものが PC を重くする原因になりうる**。メモリが 8 GB 程度の業務用 PC では特に影響が大きい。
- 要件 N-03（記録中の追加負荷を小さく）の趣旨に反するため、初版で対処すべきと判断する。

**対策案**：詳細設計 §1 で v1.1 に回していた「独自プロファイル（.wprp）の同梱」を前倒しする。バッファの量を指定して、メモリ使用量を上限（例：256 MB）に抑える。そのうえで、何秒分残るかを測り直す。

## 5. 未解決の問題：スマート アプリ コントロール

- この PC は Windows 11 の**スマート アプリ コントロール**が有効になっている。修正後にビルドし直した**自動テスト用の DLL（PerfSnap.Tests.dll）がブロックされた**（コード整合性ログのイベント 3033 / 3077）。
- 一方、配布用の **PerfSnap.exe はブロックされずに動いた**（2 回目の結合テスト）。ただし、ビルドし直すたびに判定は変わりうる。
- スマート アプリ コントロールは、一度オフにすると Windows の再インストールなしでは戻せない。セキュリティ設定なので、ツールの都合で変えることはしない。

**対策案**：
1. **自動テストは GitHub Actions（GitHub が用意する Windows 環境）で実行する**。GitHub に公開する予定なので、追加の費用なしで、この PC の設定を変えずに済む。
2. 業務用 PC への配布では、導入先のセキュリティ製品に止められる可能性がある（要件 §6-3）。**根本的な対策は、信頼された証明書によるコード署名**。導入先の管理者と相談する。

## 7. 対策後の結果（結合テスト 3 回目・4 回目）

### 7.1 行った対策

| 対策 | 内容 |
|---|---|
| 独自プロファイルの同梱 | `scripts/build-wprp.ps1` で組み込みの 6 プロファイルを書き出して 2 つに統合し、記録用メモリの量を指定できるようにした（`src/PerfSnap/Resources/PerfSnap.wprp`） |
| 設定の追加 | `recording.bufferMB`（既定 256 MB、64〜2048）、`recording.compress`（既定オン） |

3 回目は、プロファイルの要素の並び順がスキーマに合っておらず、wpr が読み込めなかった（エラー 0xc00ce014）。並び順を直し、`wpr -profiles` と `wpr -profiledetails` で読み込めることを確認してから 4 回目を行った。

### 7.2 4 回目の結果（各条件で 180 秒記録）

| プロファイル | 上限 | 非ページ プールの増加 | 空きメモリの減少 | PC 全体の CPU | 保存時間 | サイズ（圧縮後） |
|---|---|---|---|---|---|---|
| 入力遅延の調査 | 128 MB | +128 MB | −115 MB | 1.88% | 31.9 秒 | 20.0 MB |
| 詳細 | 128 MB | +128 MB | −118 MB | 2.73% | 31.2 秒 | 20.6 MB |
| 入力遅延の調査 | **256 MB（既定）** | **+256 MB** | −208 MB | 1.17% | 32.7 秒 | 43.1 MB |
| 詳細 | 256 MB | +256 MB | −226 MB | 1.83% | 34.6 秒 | 44.2 MB |

- **メモリ使用量は指定どおりに収まった。** 組み込みプロファイルの約 1.3 GB から、既定値で約 1/5 になった。→ §4 は**解消**
- 保存のファイルサイズは 1,001 MB → 39〜44 MB になった（圧縮とバッファの縮小の効果）。容量の上限 10 GB で 200 回以上残せる。
- **保持時間**：180 秒の記録では、どの条件でもバッファが一周しなかった（記録の最初から残っていた）。この PC の通常の負荷では、128 MB でも 3 分以上残る。**負荷が高いときにどこまで短くなるかは未測定**のため、余裕を見て既定値は 256 MB のままとする。

### 7.3 アプリでの確認（dotnet 経由で起動）

| ID | 結果 |
|---|---|
| IT-F2 | 待機中の CPU 0.023%、タスク マネージャー表示 3.6 MB ✅ |
| IT-F3 | ホットキーで保存成功（40.3 秒、trace.etl 38.7 MB、counters.blg あり） ✅ |
| IT-F4 | 強制終了後に再起動し、残っていた記録を片付けて監視を再開 ✅ |

- この回は、保存の途中で Windows の時刻同期により**時計が 92.7 秒進んだ**（システム ログ、Kernel-General イベント 1）。ログの時刻では保存に 2 分以上かかったように見えるが、実際の所要時間（ストップウォッチで計測）は 40.3 秒だった。遅延の検知はストップウォッチで測っているため、時刻の変化の影響を受けない。

## 8. 未解決の問題：配布用 exe がブロックされる

- 4 回目では、ビルドし直した **PerfSnap.exe がスマート アプリ コントロールにブロックされ、起動できなかった**（「アプリケーション制御ポリシーによってこのファイルがブロックされました」、コード整合性ログ 3033 / 3077）。2 回目の exe は動いたため、**ビルドのたびに結果が変わる**。
- 署名のない新しいファイルは「評判」がないため、スマート アプリ コントロールが有効な PC では止められることがある。新しくセットアップした Windows 11 では既定で有効になっている。
- そのため 4 回目は、Microsoft の署名がある `dotnet.exe` 経由でアプリを起動して、アプリの動作だけを確認した。**配布用 exe そのものの起動は、この PC では保証できない。**

**対策の選択肢**

| 選択肢 | 内容 | 注意点 |
|---|---|---|
| A. コード署名（推奨） | 信頼された証明書で exe に署名する。例：Microsoft の Azure Artifact Signing（月額制）、認証局の OV コード署名証明書 | 費用がかかる。個人では本人確認が必要 |
| B. 導入先で許可する | 導入先の管理者が、セキュリティ製品や WDAC の許可リストに登録する | 導入先ごとに手続きが必要 |
| C. 署名なしで配布する | README に「ブロックされることがある」と明記する | スマート アプリ コントロールが有効な PC では使えないことがある |
